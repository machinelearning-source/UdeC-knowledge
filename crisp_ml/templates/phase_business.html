1. Business and Data Understanding

What problem the model solves, for whom, with which data, and how success is measured.

The approved problem and its context

The University of Cundinamarca publishes its rules in long PDF documents: the Undergraduate Student Regulations, Agreement 005 of 2025 (formative experiences), the report of the Student Regulations Commission and the 2026 academic calendar. Finding one fact, such as a deadline or a requirement, means reading dozens of pages. KnowBot, the approved project, is a chatbot that answers these questions in English or Spanish and cites the document and page of every fact.

KnowBot works in two steps: it retrieves up to ten fragments of the documents and a language model writes the answer using only those fragments. The KnowBot evaluation showed that the main cause of wrong or "not found" answers is retrieval: the page that answers the question is often retrieved but not ranked first, or not retrieved at all. With exact page matching, the first fragment was from the expected page in only 46% of the 100 validation questions.

Business objectives and Machine Learning objectives

Business objectiveMachine Learning objective
More KnowBot answers cite the page that actually answers the question.Rank the candidate fragments of a question so that a fragment from the expected page is first (maximize mean reciprocal rank, MRR).
Fewer "information not found" answers when the information exists.Put the expected page among the first three fragments (Hit@3), since only the first fragments always reach the language model.
No extra cost or delay for users.A light model that scores about 40 fragments in milliseconds on a CPU, without external API calls.

Questions the model answers and learning task

  • Given a question and one candidate fragment: is this fragment from the page that answers the question? (probability between 0 and 1)
  • Given all candidates of a question: in which order should they be sent to the language model? (sorted by that probability)

Learning task: supervised binary classification used for ranking (pointwise learning to rank). Each row is a (question, fragment) pair; the target variable label is 1 when the fragment comes from the expected document and page, otherwise 0.

Data quality, relevance and sufficiency

  • Completeness: {{ quality.missing_question_fields }} missing values in the questions; every expected page exists in the index ({{ quality.questions_whose_page_is_not_indexed|length }} questions point to a page that is not indexed).
  • Duplicates: {{ quality.duplicate_questions }} duplicated questions and {{ quality.duplicate_fragments }} duplicated fragments.
  • Relevance: the questions are the kind students ask, and they were already used to evaluate KnowBot, so the labels and the business metric are the same.
  • Class imbalance: only {{ '%.1f'|format(quality.positive_rate * 100) }}% of the rows are positive ({{ quality.positive_rows }} of {{ "{:,}".format(quality.rows) }}). Models use class weights and are judged by ranking metrics, not accuracy.
  • Coverage ceiling: for {{ quality.questions_without_expected_page_in_candidates|length }} questions (ids {{ quality.questions_without_expected_page_in_candidates|join(', ') }}) no candidate comes from the expected page, so no re-ranker can fix them; they are kept and count as misses.
  • Sufficiency: {{ quality.questions }} questions is a small sample. The calendar has only {{ quality.questions_per_document['Academic Calendar 2026.pdf'] }} questions, so results for it are not reliable. This limits how complex the models can be and makes the variation between folds large; it is reported with every result.

Feasibility, limitations and risks

Technical feasibility

All features are computed locally from the existing index: vector similarity, BM25 keyword scores and exact calendar and article matches. The models are scikit-learn classifiers that train in seconds on a laptop and need no GPU. The model only re-orders fragments, so it can be added to KnowBot without changing the documents, the index or the language model.

Organizational feasibility

The documents are public, the labels were written by the team, and no personal data is used. The team knows the four documents, reviews the model's errors and maintains the KnowBot repository.

Limitations and risks. Small labeled set (risk of overfitting and of noisy model selection); labels mark one page even when a neighbouring page also answers; questions were written by the team, so real student questions may be phrased differently (distribution shift); when the documents change (a new calendar), features and labels must be rebuilt; a model that ranks a wrong page first with high confidence could make KnowBot cite the wrong rule.

Success criteria (set before modeling)

  1. Model selection: the learned model with the highest mean validation MRR over grouped 5-fold cross-validation on the 80 training questions.
  2. Business success: the selected model has a higher cross-validated MRR than KnowBot's current order, and does not lower Hit@1.
  3. Generalization: the final MRR on the 20 held-out test questions is reported once and compared with both baselines.
  4. Operation: median prediction latency below 3 seconds on the hosting service, with no external API calls.
