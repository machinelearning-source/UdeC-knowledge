5. Model Deployment

How the selected model is saved, served and used, and how it will be integrated into KnowBot.

Demonstration

The Try the model page accepts a new question in English or Spanish and shows the five fragments the model ranks first, with their probability, next to KnowBot's current order. The same function is available as a JSON API.

Dependencies and execution

Python 3.12; Flask, gunicorn, scikit-learn, pandas, numpy, joblib, matplotlib, faiss-cpu, fastembed (ONNX embeddings on CPU) and langchain-community (to read the FAISS index). Exact versions are in requirements.txt. No API key is needed.

python -m venv .venv
.venv\Scripts\activate            # Windows  (source .venv/bin/activate on macOS/Linux)
pip install -r requirements.txt
python scripts/build_dataset.py   # Phase 2: rebuild the dataset (optional, already included)
python scripts/train.py           # Phases 3-4: retrain and re-evaluate (optional, already included)
python app.py                     # open http://127.0.0.1:5000

In production the app runs with gunicorn app:app. The first request after a restart waits while the embedding model loads (about 10–30 seconds); the page shows a notice until then.

Hosting: why Render and not Streamlit

KnowBot itself is not moved: it remains deployed on Streamlit Community Cloud, which hosts only Streamlit applications. The re-ranker is a separate Flask service, so it is deployed on Render, which runs Python web services on its free plan and builds them directly from the GitHub repository through render.yaml (build command, gunicorn start command and /health check), so the deployment is versioned and reproducible.

Fitting in 512 MB of memory

Loaded as usual, the multilingual embedding model made the app use about 740 MB, above the 512 MB of the free instance. Two changes in knowbot/embeddings.py bring it to about 355 MB without changing any result:

PartProblemChange
Vocabulary table (250,002 × 384)183 MB in float16, expanded by onnxruntime to float32Moved out of the ONNX graph into a memory-mapped file; only the rows of the question's tokens are read
TokenizerAbout 250 MB with tokenizer.jsonThe model's original SentencePiece file, a few MB, with the same token ids

Both were checked against the standard model: identical token ids on 400 texts (the 100 questions, the 290 fragments and edge cases) and a maximum difference of 0.0 between the vectors of the 100 questions, so the features, the model and every reported metric are unchanged.

Keeping the two services apart lets the model run in shadow mode without any risk to the chatbot students use. Limitations of the free plan: the service sleeps after about 15 minutes without traffic, so the first visit can take about a minute to wake it up, and the files in logs/ are reset on every restart, so the monitoring shown in Phase 6 demonstrates the procedure rather than a long history.

User instructions

  1. Open Try the model.
  2. Write a question about the regulations, Agreement 005, the Commission report or the 2026 calendar, or click an example.
  3. Read the left column (model) and compare it with the right column (KnowBot's current order). The probability shows how sure the model is; below 0.30 it is unsure.
  4. Answer "Was the first fragment the right one?" to send feedback.

Integration plan into KnowBot (the information system of Activity 2)

  1. Shadow mode (now): KnowBot calls the re-ranker after its retrieval step and logs both orders, but keeps sending its own order to the language model. This is the safe option, because the test set did not confirm a gain.
  2. Collect labels: the feedback buttons of KnowBot and of this demo, plus questions reviewed by the team, become new labeled questions.
  3. Retrain and re-test: with at least 200 labeled questions, repeat Phases 2–4. If the model beats KnowBot's order on a new test set, switch it on.
  4. Gradual switch: use the model order for the first fragments only when its top probability is at least 0.5, otherwise keep KnowBot's order.

Technically, the integration is one function call in KnowBot's retrieve_documents: the candidates are already there; the re-ranker adds the features, scores them and returns the new order.

Monitoring, incident reporting and user feedback

  • Prediction log: every prediction is written to logs/predictions.csv (time, source, question length, number of candidates, top probability, top document and page, agreement with KnowBot's order, latency, error). The prediction log stores the length of the question, not its text; the feedback form stores the question, because it is needed to label it.
  • Feedback: the yes/no answer and an optional comment go to logs/feedback.csv.
  • Incidents: errors are logged with the input length and shown on the monitoring page. Users report problems through the feedback comment or to the KnowBot team through the GitHub issues of the repository. An incident is reviewed within one week; a wrong deadline or requirement shown first is handled first.
  • Health check: /health returns whether the model is loaded and can be checked by the hosting service or an external monitor.
